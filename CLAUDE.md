# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm run dev        # start Vite dev server (defaults to :5173; if that port is busy Vite silently
                    # picks 5174/5175/... — always check the printed URL, don't assume 5173)
npm run build      # production build to dist/ (runs Vite/esbuild's own TS transpile — does NOT
                    # type-check; a type error will NOT fail this command, see typecheck below)
npm run preview    # serve the production build locally
npm run lint       # oxlint (config: .oxlintrc.json) — also lints TS/TSX, see TypeScript section
npm run typecheck  # tsc --noEmit — the ONLY command that actually checks types; run this before
                    # claiming a change is done, build succeeding is not proof the types are right
```

There is no test suite/test script configured in this repo.

On Windows, a previous `npm run dev` that wasn't cleanly killed will keep holding its port and silently serve stale code to anything hitting `:5173`. If dev-server output looks wrong, check for orphaned `node.exe` processes (`Get-Process node`) before debugging the app itself.

`vite.config.ts` sets `build.rollupOptions.output.manualChunks` as a **function**, not the plain `{ vendor: [...] }` object form — this Vite version builds on Rolldown, which throws (`TypeError: manualChunks is not a function`) if given the object form classic Rollup accepts. The function groups `react`/`react-dom`/`react-router-dom`/`@tanstack`/`axios`/`zustand`/`sonner`/`react-hook-form` into one `vendor` chunk via a `node_modules/<pkg>/` regex, separate from app code — so a code change doesn't invalidate the browser cache for the (unchanged) vendor bundle (confirmed by `npm run build`: the app-code chunk dropped from 287 KB to 60 KB once `vendor` was split out, with `vendor` itself at 303 KB/95 KB gzip). If you add a new major dependency that should also live in `vendor`, add it to the regex in `vite.config.ts`, not by copying the old object syntax.

## What this is

A Tik Tak e-commerce **admin panel** UI built from a Figma design (Vite + React 19 + **TypeScript**), wired to a real backend at `VITE_API_BASE_URL` (see `.env.example`; full endpoint reference in `docs/API.md`). All screens/text are Azerbaijani. Every list page fetches from the real API via **TanStack Query** (`useQuery`/`useMutation`, see below) — there is no offline/mock mode. Auth is real: the Login page calls `POST /auth/admin/login` via the `useAuthStore` zustand store (`src/store/useAuthStore.ts`), and all `AdminLayout` routes are wrapped in a `RequireAuth` route guard (`src/routes/RequireAuth.tsx`) that redirects to `/login` when no access token is stored. Login itself reports a failed attempt (wrong password, empty fields) as a toast, same as every other page — no inline error text anywhere in the app; a successful login also toasts ("Hesaba uğurla daxil olundu") before navigating to `/sifarisler`. Logging out (`Sidebar.tsx`'s `ConfirmModal` confirm handler) toasts "Hesabdan çıxış edildi" the same way, right before calling `logout()` + `navigate('/login')`. Its phone/password inputs are `lucide-react` icons absolutely positioned inside a `.inputWrap` — `Phone` fixed on the left of the phone field; the password field has both `Lock` fixed on the left AND a clickable `Eye`/`EyeOff` on the right that toggles `type="password"`↔`"text"`, so it carries all three of `.hasLeadingIcon` + `.hasTrailingIcon` + a `Lock` sibling at once. `.hasLeadingIcon`/`.hasTrailingIcon` on `.input` just add padding so the text doesn't sit under whichever icon(s) are present; reuse this wrapper pattern (not a new component) if another form ever needs an icon-in-input. `src/pages/Login/` has exactly three subfolders — `hooks/`, `components/`, `styles/` — plus the page root `index.tsx` (see **`src/pages/`** below for why it's `index.tsx` directly rather than `Login.tsx` + a thin barrel):
- `hooks/useLoginForm.ts` (+ its own `index.ts` barrel, same as `Campaigns/hooks/index.ts` re-exporting `useCampaignsPage`) owns all the form's state/logic: the `react-hook-form` instance (`register`/`handleSubmit`), the `showPassword` toggle, and the submit/invalid handlers — returns a small `{ register, submit, isSubmitting, showPassword, togglePassword }` object, `submit` already being the `handleSubmit(onSubmit, onInvalid)`-bound handler so `LoginForm.tsx` just does `<form onSubmit={submit}>`. It's **`react-hook-form`**, matching every other form in the app (see `<Name>Form` under **CRUD modal pattern** below), not a hand-rolled `useState`-per-field form; validation failures (empty/whitespace-only phone or password) are surfaced via `handleSubmit`'s second `onInvalid` callback calling `toast.error('Telefon və parolu daxil edin')`, keeping the same "no inline error text, only a toast" rule the rest of the app follows (see **Error handling**) even though this form isn't wired to TanStack Query.
- `components/` holds three sibling folders — `LoginForm/`, `PhoneField/`, `PasswordField/` — each its own `Name.tsx` + `index.ts`, flat (not nested inside one another) even though `PhoneField`/`PasswordField` are only ever rendered by `LoginForm.tsx`. `PhoneField`/`PasswordField` each take a typed `register: UseFormRegister<LoginFormValues>` prop (`LoginPhoneFieldProps`/`LoginPasswordFieldProps` in `src/types/auth/`, per **Every component `Props`/state interface in the app now lives in `src/types/`** below); `PasswordField` additionally takes `showPassword`/`onToggle` since the visibility toggle button lives inside it, not in `LoginForm.tsx`. The password-visibility toggle and the submit button both render through the shared `Button` component (`variant="ghost"` for the toggle, default `variant="solid"` + `fullWidth` for submit) rather than bare `<button>` tags, same as every other form in the app.
- `styles/` holds every `.module.css` in the page — `Login.module.css` (page shell), `LoginForm.module.css` (just `.submitBtn`), `PhoneField.module.css`, `PasswordField.module.css` — same "CSS lives in its own folder, not next to its `.tsx`" exception the four CRUD pages use (see **`styles/`** under **`Campaigns`, `Categories`, `Products`, and `Users` have all been decomposed...** below), so every import is the `@/pages/Login/styles/<Name>.module.css` alias form, not a relative path. `PhoneField.module.css`/`PasswordField.module.css` duplicate the shared `.field`/`.inputWrap`/`.input`/`.hasLeadingIcon`/`.leadingIcon` rules between them rather than factoring them into one shared file — same reasoning as `Users`'s `.roleBadge` duplication: CSS Modules scope class names locally per file, so the duplication costs nothing and keeps each field self-contained. `Login.module.css`'s `.right` is `flex items-center justify-center` (not `justify-start`) so `.formWrap` sits centered in the narrow right-hand column rather than pinned to its left edge — with the column itself only 40% width (`.page`'s `60fr 40fr` grid), centering still keeps the form close to the center divider without the lopsided empty-space-to-the-right look `justify-start` produced on a wide viewport; don't reintroduce an asymmetric `padding-left` bump on `.right` to fake a "near the border" look, centering handles it. `.formWrap`'s `max-width` (490px) and the form's own input/label/button sizing (`PhoneField`/`PasswordField`/`LoginForm`'s `.input`/`.field`/`.submitBtn` font-sizes and padding, plus the `lucide-react` icon `size` props in the field components) were bumped up from the original Figma-derived values on request, purely a visual size increase — keep the three field-CSS files' paddings/font-sizes in sync with each other if tuning further, they're meant to look identical.

Page components are lazy-loaded (`React.lazy` in `src/routes/AppRoutes.tsx`) so each route ships as its own JS chunk.

The whole `src/` tree is TypeScript (`.ts`/`.tsx`, zero `.js`/`.jsx` remaining) — see the dedicated **TypeScript** section below for the type policy, `src/types/` layout, and the handful of genuinely advanced spots (module augmentation, the `api` cast) before touching typed code.

## Architecture

**Path alias**: `@` → `src/`, configured in **both** `vite.config.ts` (`resolve.alias`) and `tsconfig.json` (`paths`) — keep them in sync if changed. All cross-folder imports use `@/...`; only same-folder sibling imports (e.g. a component importing its own `.module.css`) stay relative. There is no `jsconfig.json` — it was deleted when `tsconfig.json` took over path resolution; don't re-add it.

**Import paths stop at the folder, not the file**: every component/page/util folder has an `index.ts` that re-exports its own `Name.tsx`/`.ts` (e.g. `shared/components/Modal/index.ts` is `export { default } from './Modal'`), so consumers import `@/shared/components/Modal`, never `@/shared/components/Modal/Modal`. `Table`'s `index.ts` re-exports all three of its bindings (`export { default, Table, TableEmptyRow } from './Table'`) since the module has both a default and named exports. This is a barrel **per folder only** — there is deliberately no single top-level `shared/components/index.ts` re-exporting everything, because every component also imports its own `.module.css` (a side-effecting import), and a many-to-one barrel would make Rollup/Vite unable to tree-shake unused components out of a chunk that only needed one or two, undermining the per-route code-splitting described under **Routing**. When adding a new component/page/util folder, add its own single-file `index.ts` the same way — don't add exports to some other folder's barrel and don't create a barrel that re-exports more than one sibling folder.

**Entry point**: `src/app/main.tsx` (referenced directly by path in `index.html`, not the `@` alias, since it's the one file Vite needs before any bundling/aliasing exists) renders `<ErrorBoundary><App/></ErrorBoundary>` — the boundary sits here, outside everything, so it also covers `App.tsx` itself and its providers, not just the routed pages. No `<StrictMode>` — removed deliberately, not an oversight. `src/app/App.tsx` mounts `<QueryClientProvider>` → `<BrowserRouter>` around `<AppRoutes />` + a sibling `<Toaster/>` (sonner).

**Routing**: the actual route tree lives in `src/routes/AppRoutes.tsx`, kept separate so `App.tsx` stays a thin shell. react-router-dom, Azerbaijani paths — `/login`, `/sifarisler`, `/kampaniyalar`, `/kateqoriyalar`, `/mehsullar`, `/istifadeciler`. `/login` is wrapped in `RedirectIfAuth` (bounces an already-logged-in admin to `/sifarisler`). All other routes are nested under a `RequireAuth` layout route (redirects to `/login` when unauthenticated), which itself nests them under `AdminLayout` via a layout route + `<Outlet>`. `/` redirects to `/sifarisler`; unmatched paths (`*`) render `src/pages/NotFound/NotFound.tsx` (a standalone full-page 404, not wrapped in `AdminLayout`, same pattern as `Login`) instead of redirecting — this is intentional so a broken/typo'd URL is visibly a 404 rather than silently bouncing to Orders. Auth state lives in a zustand store, not a React context/provider, so nothing wraps the router for auth. Every page component in `AppRoutes.tsx` is `lazy(() => import(...))`; the whole `<Routes>` tree is wrapped in one `<Suspense fallback={<Loading fullScreen/>}>` — reuses the same shared `Loading` spinner pages use for data fetches, so a route-chunk load and a slow API call look the same to the user; `fullScreen` centers it in the viewport since at that point it's the only thing rendered on the page, vs. the default inline mode pages use next to their own content. Don't add page imports as static `import Foo from '...'` — follow the `lazy(...)` pattern or the chunk-splitting benefit is lost for that route.

**Error handling**: three distinct, deliberately separate mechanisms — don't conflate them. (1) A bad **URL** (`*` route) renders `NotFound`. (2) A **JS exception thrown while rendering** anywhere in the tree is caught by `src/shared/components/ErrorBoundary/ErrorBoundary.tsx` (a class component using `getDerivedStateFromError`/`componentDidCatch`, the only place in the codebase that needs to be a class — error boundaries can't be hooks; its `override` keywords on `state`/`componentDidCatch`/`render` are required by `noImplicitOverride`, see **TypeScript**) wrapping `<App/>` in `src/app/main.tsx` (see **Entry point** above, not inside `App.tsx` — it needs to sit above the providers too). The fallback UI (icon + message + a plain `window.location.href = '/sifarisler'` button, not `useNavigate` — hooks aren't available in a class component's `render()`) lives directly inside `ErrorBoundary.tsx`/`ErrorBoundary.module.css`, there's no separate error page/route for it. (3) **API/network failures** are *not* funneled through the error boundary — `src/services/axiosInstance.ts`'s `handleError` just normalizes them to a plain `Error` and rejects the promise; every query/mutation error is toasted **globally and automatically** by `src/lib/queryClient.ts`'s `QueryCache`/`MutationCache` `onError` (`toast.error(err.message)`) — pages never write their own error-toast code, a bare `try { await mutateAsync(...) } catch {}` in a page is just there to stop `setFormOpen(false)`/`setDeleteTarget(null)` from running on failure, not to show anything. Success toasts are the one thing pages DO call explicitly, in each mutation's own `onSuccess`, phrased in the Azerbaijani completed/passive tense ("Kateqoriya yaradıldı", "Məhsul silindi", "Sifariş statusu yeniləndi") — never a progress tense ("yaradılır", "silinir"). `createMutation.isPending`/`updateMutation.isPending` (OR'd together) drives the submit button's `disabled` + "Göndərilir..." label — there's no separate hand-rolled `submitting` state anymore.

**Folder convention**: every component/page is its own folder containing `Name.tsx` + `Name.module.css` + an `index.ts` barrel side by side — no bare `.tsx` files outside that pattern, no CSS-in-JS, no Tailwind. Plain data/logic files (services, adapters, hooks, constants) are `.ts`; anything that returns JSX is `.tsx`. See **Import paths stop at the folder, not the file** below for what the `index.ts` looks like and why it's one-per-folder, not a shared top-level barrel.

- `src/shared/components/` — generic reusable UI primitives: `Button`, `Modal`/`ConfirmModal` (`role="dialog"`/`role="alertdialog"` + `aria-modal`, focus the close/cancel button on open, `Escape` key calls `onClose`/`onCancel` — both wired via a `useEffect` keyed on `open`, not a focus-trap library; `.card` has `max-height: calc(100vh - 32px)` + `overflow-y: auto` with the scrollbar hidden the same way `Table`'s `.scroll` does (`scrollbar-width: none` + `::-webkit-scrollbar{display:none}` — scroll still works via wheel/touch, just no visible track), added after `Orders`' detail modal — the tallest content of any modal in the app — could overflow past the viewport with no way to reach the rest; `ModalProps` also grew an optional `className`, appended after `styles.card`/`styles.cardWide` in `Modal.tsx`'s class list, so one specific page can widen/restyle just its own modal (e.g. `Orders`' `styles.wideModal`, see below) without bumping `.cardWide` itself and affecting every other page's `wide` modal), `Badge`, `StatCard`, `ActionMenu`, `Table`, `Loading` (5-bar equalizer spinner — pure CSS, no icon/spinner library: five `.bar` spans, each a different badge color (green/blue/purple/amber/green), running the same `eq` height keyframe with a staggered `animation-delay` (0/0.1/0.2/0.3/0.4s) so the heights ripple across the row instead of pumping in unison; bar width/gap/min-height/max-height are all CSS custom properties (`--bar-width`/`--bar-gap`/`--bar-min`/`--bar-max`) read by one shared `.bar`/`@keyframes eq` definition, so the `.fullScreen` variant scales the whole thing (bar size *and* travel distance together) with one override block instead of duplicating markup or keyframes; + a "Yüklənir..." text that breathes (opacity animation) rather than sitting static, stacked/centered layout, not inline; `fullScreen` prop switches `.wrap` to `position: fixed; inset: 0` (not just a tall `min-height` box in normal flow) so the route-level `Suspense` fallback is pinned dead-center of the actual viewport regardless of surrounding scroll/layout state, and roughly doubles every `--bar-*` value since it's the only thing on screen at that point — default/no-prop mode is what pages use for their own `isLoading` query state, see **Routing**. This went through several iterations before landing here (a conic-gradient ring, then a 4-dot bounce, then an orbiting-satellite design were each tried and replaced) — if redesigning again, verify any candidate visually (e.g. a headless-Chrome screenshot of an isolated HTML reproduction) before wiring it into the component, since CSS-only animations can't be checked by `typecheck`/`lint`.), `Thumbnail` (the `imageUrl` → `<img>` / fallback-emoji-over-`color` pattern from **CRUD modal pattern** below, `size="sm"` for table cells (default, 40px) or `size="lg"` for detail-modal headers (56px) — the `<img>` itself runs `imageUrl` through `@/utils/ResizeThumbnailUrl`'s `resizeThumbnailUrl(url, pixelSize * 2)` before rendering, plus sets explicit `width`/`height` and `loading="lazy"`/`decoding="async"`; the backend's `img_url` already comes pre-resized via Cloudflare Image Resizing (`/cdn-cgi/image/width=600,height=400,.../...`) but at a fixed 600×400 regardless of where it's displayed, so without this a 40-56px thumbnail was downloading a ~600×400 image — `resizeThumbnailUrl` rewrites just the `width=`/`height=` values inside that URL segment to the actual on-screen size (×2 for retina), leaving quality/format alone; URLs that don't contain that segment pass through unchanged), `ErrorBoundary` (the one class component in the app — see **Error handling**), `FormField`/`FormInput`/`FormTextarea`/`FormSelect` (the labeled-field pieces every CRUD form's `<input>`/`<textarea>`/`<select>` is built from, extracted on request from the near-identical JSX+CSS `CampaignForm`/`CategoryForm`/`ProductForm` each had before — `FormField` is just the `<label>` + `flex flex-col gap-2` wrapper, taking `label`/`children`; `FormInput`/`FormTextarea`/`FormSelect` each carry the same visual CSS — `border-radius`/`background: var(--color-subtle-bg)`/`padding`/focus border-color — duplicated once per component's own `.module.css` rather than shared, consistent with how small identical blocks are handled elsewhere in this app (see `Users`'s `.roleBadge` under **`Campaigns`, `Categories`, `Products`, and `Users` have all been decomposed...** above). All three are typed `ComponentPropsWithRef<'input'|'textarea'|'select'>` (a bare `type` alias, not an `interface extends {}` — an empty-body interface here would just be a worse spelling of the same type) rather than wrapped in `forwardRef`, same reasoning as `Button` below — this is what lets `{...register('name')}` (react-hook-form's own `ref` included) pass straight through to the real DOM node. A CRUD form's own JSX composes them as `<FormField label="Ad"><FormInput {...register('name', {required: true})} /></FormField>` — `FormField` never knows about react-hook-form at all, the `register()` spread happens entirely at the call site. This was deliberately **not** taken further into one fully generic schema-driven `<ResourceForm fields={...} />` — three forms, one of which (`Product`) has a meaningfully different field set, isn't a strong enough case for that; see the `Column` type's own "deliberately not generic" reasoning under **TypeScript** for the same judgment call applied elsewhere in this codebase.). `src/shared/hooks/` sits as a sibling of `shared/components/` (not inside it) for cross-cutting hooks (`useTitle`, `useDebounce`, `usePagination`, `useCrudModal`) — flat `.ts` files, no per-hook folder/CSS since hooks have no markup; `usePagination`/`useDebounce`/`useCrudModal` are generic (`usePagination<T>`, etc., see **TypeScript**). There is no `ErrorText`/inline-error component and no hand-rolled data-fetching hook — data fetching is TanStack Query (`useQuery`/`useMutation`, see **Data fetching** below), all error/success feedback is a toast (see **Error handling**).
- `src/types/` — the TypeScript type definitions, one file per resource (`category.ts`, `product.ts`, `campaign.ts`, `order.ts`, `user.ts`, plus `auth.ts`, `api.ts`, `common.ts`) and a thin `index.ts` barrel. See the **TypeScript** section below for what belongs here vs. what stays colocated with the code it describes.
- `src/utils/` — `Pagination`, `FormatDate`, and `ResizeThumbnailUrl` live here by project convention, not in `shared/`. Every entry is its own folder (`Pagination/Pagination.tsx`+css, `FormatDate/formatDate.ts`, `ResizeThumbnailUrl/resizeThumbnailUrl.ts`) even for a plain non-component function — keep new utils consistent with this, don't drop a bare `.ts` file directly in `src/utils/`.
- `src/components/` — layout-only chrome (`Sidebar`, `Header`), used exclusively by `AdminLayout`.
- `src/layouts/` — the sidebar+header shell wrapping every non-login page. `AdminLayout.tsx` + `AdminLayout.module.css` sit flat directly in `src/layouts/` (no nested `AdminLayout/` subfolder) since it's the only layout in the app — add a per-layout subfolder only if a second layout is ever introduced.
- `src/pages/` — one folder per route. `src/pages/Protected/<Name>/` (`Orders`, `Campaigns`, `Categories`, `Products`, `Users`) holds every page behind `RequireAuth`; put any new authenticated page there. Note the capital `Protected` — every folder under `src/pages/` is PascalCase (matches `Login`, `NotFound`); a lowercase `protected` previously existed on disk while git already tracked it as `Protected`, which is invisible to `git status` on a case-insensitive filesystem (Windows/macOS default) but breaks imports on a case-sensitive one (Linux CI/prod) — if a folder here ever looks lowercase on disk, that's the bug to fix, not a valid alternate spelling. `src/pages/Login/` sits at the top level, unwrapped — it's the one route wrapped in `RedirectIfAuth` instead of `RequireAuth`, so grouping it under a generic folder wasn't worth it for a single page. Its root is `index.tsx` directly (the component itself, not `Login.tsx` + a thin `index.ts` barrel) — the same shortcut the five `Protected` pages use (see **`Campaigns`, `Categories`, `Products`, and `Users` have all been decomposed...** below), extended to `Login` on request. It gets three of the five-page subfolders — `hooks/`, `components/`, `styles/` (see **What this is** above for what's in each) — but deliberately **not** `queries/`/`constants/`/`table/`/`pagination/`, since there's no list data, no CRUD mutations, and nothing to paginate; those folders would sit empty.
- `src/services/` — the API layer. `axiosInstance.ts` creates one shared `axios.create()` instance and holds the only two response handlers (`handleSuccess`/`handleError`, both a few lines); every other service file (`categoryService.ts`, `productService.ts`, `campaignService.ts`, `orderService.ts`, `userService.ts`, `authService.ts`, `uploadService.ts`) just calls `api.get<T>/post<T>/put<T>/delete<T>` on it — no per-file error handling, no custom client class. See **TypeScript** for what `T` is doing there.
- `src/lib/adapters/` — one file per resource (`category.ts`, `product.ts`, `campaign.ts`, `order.ts`, `user.ts`) with `mapXFromApi`/`mapXToApi` pairs that translate between the API's field names (snake_case, `title` vs `name`, `category_id` vs nested `category`) and the shape pages/JSX expect. Each pair is typed `(x: XApi) => X` / `(form: XForm) => XPayload`, all four types imported from `src/types/`.
- `src/lib/auth/session.ts` — localStorage read/write/clear for the access/refresh tokens and cached profile.
- `src/lib/constants/` — `productTypes.ts` (`ProductType` union → Azerbaijani labels + badge color) and `orderStatus.ts` (`OrderStatus` union → Azerbaijani labels + badge color). These are the **single source of truth** for the two union types — `src/types/product.ts`/`order.ts` re-export them type-only rather than redefining, see **TypeScript**.
- `src/store/useAuthStore.ts` — zustand store (`create<AuthState>()`, no Provider needed), owns `login`/`logout`/`profile`/`isAuthenticated`. Also registers a module-level `window.addEventListener('storage', ...)` that re-syncs `isAuthenticated`/`profile` from `localStorage` whenever another tab logs in/out — the browser only fires `storage` on tabs *other than* the one that made the change, so this is what keeps a second open tab from staying "logged in" after you log out in the first one; `RequireAuth` picks up the resulting state change automatically since it already subscribes to `isAuthenticated`.
- `src/store/useThemeStore.ts` — zustand store owning dark/light mode (`theme: 'light' | 'dark'`, `toggleTheme()`). Deliberately does **not** hold the actual colors — it only decides which set of CSS custom properties is active by setting `data-theme="dark"`/`"light"` on `document.documentElement` (see **Design tokens** below for the CSS side); React re-renders only for the toggle button's own icon swap, not for the color change itself, which is pure CSS. Initial value comes from `localStorage['admin-theme']` if set, else `window.matchMedia('(prefers-color-scheme: dark)')` — `applyTheme()` (a plain module function, not part of the store's state) runs once at store-creation time (module load) and again on every `toggleTheme()` call, so the `<html>` attribute and `localStorage` are always in sync with the store's `theme` value, never just one or the other.
- `src/routes/` — `RequireAuth.tsx` and `RedirectIfAuth.tsx` route guards used in `App.tsx`, both read `useAuthStore` directly.
- `src/app/` — `main.tsx` (entry point, referenced by `index.html`) and `App.tsx` (providers + router shell) — the only two files in the whole codebase not under `src/pages|shared|components|...`, kept together since they're both "bootstrap the app" concerns, not features.
- `src/assets/images/` — illustrations from the Figma design (`login-img.webp`, `delete-img.webp`), imported and rendered directly as `<img src={...}>`. These were originally exported from Figma as `.svg`, but were actually a raster PNG embedded as base64 inside a single `<image>` tag (a common Figma-export artifact for non-vector layers) — not real vector graphics, so they gzipped poorly (~25%) and were by far the largest assets in the build (404 KB / 124 KB, bigger than the entire JS bundle). Converted to `.webp` at quality 80 (`sharp-cli`, visually identical to the original at normal viewing size — these are flat-color illustrations, not photos, so lossy WebP has plenty of headroom): 21 KB / 24 KB, a ~95%/~80% reduction from the original `.svg`. If a new Figma illustration is added here, check whether it's real vector markup or another base64-wrapped raster before committing it as `.svg` — `grep base64` the file to tell the difference — and export/convert raster ones to `.webp` instead.
- `src/assets/icon/webico.png` — the source Tik Tak logo artwork (677×369, full lockup with "Tíktak"/"Tərəvəz Sifarişi" text), kept as-is for reference; **not** imported anywhere in the app. The actual favicon files derived from it live in `public/` (`favicon-16.png`, `favicon-32.png`, `favicon-48.png`, `apple-touch-icon.png`), referenced from `index.html`'s `<link rel="icon">`/`<link rel="apple-touch-icon">` tags — Vite serves everything in `public/` from the site root unchanged, so `/favicon-32.png` resolves directly to `public/favicon-32.png`. The three small sizes are cropped to **just the basket graphic** (text stripped out) — at 16-32px the full lockup's text turns into illegible mush, so the crop trades the wordmark for a basket shape that actually reads as an icon in a browser tab; `apple-touch-icon.png` (180px) keeps the full lockup since text is still legible at that size. **API layer conventions** (see `docs/API.md` for the full endpoint reference): base URL comes from `VITE_API_BASE_URL` (`.env`, not committed — see `.env.example`). `src/services/axiosInstance.ts` is the single place that knows about HTTP: a request interceptor attaches `Authorization: Bearer <token>`, and the response interceptor's `handleSuccess` unwraps the standard `{message, data, result}` envelope (falls back to the raw body when there's no `data` key, e.g. `GET /orders/admin/stats`) so every service function already resolves to the usable payload — callers never touch `response.data`. On a `401`, `handleError` transparently refreshes the access token via `POST /auth/refresh` (`refreshAccessToken()`, concurrent 401s share one in-flight refresh call via `refreshPromise` so a burst of requests doesn't fire the refresh endpoint multiple times) and retries the original request exactly once (`original._retry` guards against a retry loop); if the refresh itself fails, or there's no refresh token stored, it calls `clearSession()` + `useAuthStore.getState().logout()`. `POST /auth/admin/login` is the one request that opts out of this via `{ skipAuthRetry: true }` in `authService.ts` — a wrong-password 401 on login must not trigger a refresh attempt or a logout (`skipAuthRetry`/`_retry` are not real Axios fields — they're added to `AxiosRequestConfig` via a `declare module 'axios'` augmentation in `src/types/api/AxiosRequestConfig.ts`, see **TypeScript**). The backend's own error messages come back in **English** (e.g. `"Password is wrong!"`, `"Auth access error"`) — `handleError` never surfaces them directly; `getErrorMessage()` maps the HTTP status code to a fixed Azerbaijani string instead (`STATUS_MESSAGES`, plus a special case for `401` that reads "Telefon və ya parol yanlışdır" on the login request vs "Sessiya bitib, yenidən daxil olun" everywhere else, and two FK-constraint special cases for `400`/`422` matched by request method + URL rather than status code alone: `isProductDelete` (`DELETE /admin/products/:id`, "Bu məhsul mövcud sifarişlərdə istifadə olunduğu üçün silinə bilməz") and `isCategoryDelete` (`DELETE /admin/categories/:id`, "Bu kateqoriya mövcud məhsullarda istifadə olunduğu üçün silinə bilməz") — both exist because the backend rejects deleting a row something else still references with a bare 400/422 and no distinguishing body, so without this the admin saw the generic "Məlumatlar düzgün deyil" and read it as a bug rather than an explainable FK conflict), so every toast in the app — success or error — is guaranteed to be in Azerbaijani regardless of what the backend actually said. If a third resource ever needs this (e.g. deleting a campaign that's still referenced somewhere), add another `is<X>Delete` check following the same method+URL-regex pattern, don't try to distinguish these by response body content — the backend doesn't send one worth parsing. When adding a new endpoint, don't reach for `error.response.data.message` — extend `STATUS_MESSAGES` if a new status code needs its own wording. Every other failure just rejects the promise — no redirect, no error-boundary involvement (see **Error handling** above for why those two are kept separate from plain API errors). Category/Product/Campaign **create** endpoints use a **singular** URL (`/admin/category`) while **update/delete/list** use the **plural** form (`/admin/categories/:id`) — this is a real backend quirk, not a typo; each `src/services/*Service.ts` file already encodes it correctly, don't "fix" it to be consistent.

**Data fetching** (TanStack Query, `src/lib/queryClient.ts`): `defaultOptions.queries.staleTime` is set to 15s (not TanStack's default of 0) — navigating back to a page you were just on within 15s reuses the cached data instead of refetching; a create/update/delete's `invalidateQueries` still forces an immediate refetch regardless of `staleTime`, so mutations always show fresh data. Every list page reads via `useQuery({ queryKey: [...], queryFn: ... })` and writes via `useMutation`, invalidating the relevant `queryKey` in `onSuccess` instead of hand-patching local array state. Query keys are the resource name in English, plural, matching the service module (`['categories']`, `['products']`, `['campaigns']`, `['orders']`, `['orderStats']`, `['users']`) — reuse the exact same key when two pages need the same resource: `Products/queries/useProductsData.ts` queries `['categories']` for its category dropdown with the *same key* `Categories/queries/useCategoriesData.ts` uses for its own list, so TanStack Query dedupes/shares that cache entry between the two pages instead of fetching it twice. **The `queryFn` for a shared key must produce the identical shape everywhere it's used** — TanStack Query caches by key alone, not by `queryFn`, so if two components register different mappings under the same key, whichever mounts first "wins" and the other silently renders the wrong shape until the cache goes stale (this was a real bug: `Products` used to fetch raw `listCategories()` under `['categories']` while `Categories` mapped it through `mapCategoryFromApi` under the same key — fixed by making both use the mapped version; TypeScript does NOT catch this class of bug on its own, since both queryFns still type-check individually — the discipline of reusing the exact same queryFn is still on you). `src/components/Sidebar/Sidebar.tsx` used to prefetch each page's data via `queryClient.prefetchQuery` on a nav link's `onMouseEnter` (a `PREFETCH` map keyed by route, mirroring each page's own `queryKey`/`queryFn`) — removed by request (hovering a nav link fired a real network request, which wasn't wanted); `Sidebar.tsx` no longer imports `useQueryClient` or any service/adapter. If prefetching is reintroduced later, keep reusing the exact same `queryKey`/`queryFn` pairs the target page's own `useQuery` uses, per the shared-cache-key rule above — don't invent a different shape "close enough" for prefetching. `Orders/queries/useOrdersData.ts` similarly runs two independent `useQuery` calls (`['orders']`, `['orderStats']`) rather than one combined `Promise.all` fetch — simpler than trying to merge two unrelated pieces of state into one query result; `orderStats`'s query is typed `Partial<OrderStats>` at the fetch boundary (see **TypeScript**) because the backend can omit counters. Mutation success/error are NOT handled per-page (see **Error handling**); the only page-level `try/catch` around `mutateAsync` exists to gate closing the modal/dialog on success. `Orders/index.tsx`'s detail modal keeps a `selectedId` (not a snapshot object) and derives `selected = orders.find(o => o.id === selectedId)` — after a status-change mutation invalidates and refetches `['orders']`, `selected` automatically reflects the fresh data (including `user`, which the status-update response itself omits but the list response always includes) with no manual merging. The status-update mutation in `Orders/queries/useOrderMutations.ts` is also **optimistic**: `onMutate` patches the cached `['orders']` entry immediately (so the status `<select>`/badge update with no visible lag) and rolls back via the `previousOrders` returned from `onMutate` if the request fails — a real UX bug without it: the dropdown visibly "snapped back" for ~2s while the network round-trip completed.

**`invalidate()` inside a mutation's `onSuccess` must not be `await`ed** (`Campaigns`/`Categories`/`Products`'s `use<Name>Mutations.ts` — this was a real, reported perceived-lag bug, not a hypothetical): each page's `handleSubmit`/`confirmDelete` (in `hooks/use<Name>sPage.ts`) does `await createMutation.mutateAsync(...)` and only closes the modal afterward, and TanStack Query does not resolve a mutation's `mutateAsync()` promise until its own `onSuccess` callback finishes — so an `onSuccess: async () => { await invalidate(); toast.success(...) }` makes the modal sit open (button stuck on "Göndərilir...") for **two** sequential network round-trips back to back: the write itself, then the refetch `invalidateQueries` triggers. Dropping the `await` (`onSuccess: () => { invalidate(); toast.success(...) }`) lets the modal close and the toast fire the instant the write succeeds; `invalidateQueries` still runs and the list still refreshes, just a beat later in the background instead of blocking the UI on it. `Orders`' `updateStatus` never had this problem since it's optimistic (see above) and called via plain `.mutate()`, not an awaited `.mutateAsync()`. If a new page's mutations hook is added, default to the non-awaited form — only await `invalidate()` if something genuinely depends on the refetched data being in cache before the next line runs.

**Consistent page chrome via CSS vars**: `AdminLayout.module.css`'s `.page` is a `height: 100vh` flex column (`.headerBar` natural height + `flex-shrink: 0`, `.bodyBar`/`.main` both `flex: 1` + `min-height: 0`). This went through four iterations, each fixing a real reported bug rather than a hypothetical — worth reading in order since two of them look reasonable in isolation and were only proven wrong by an actual screenshot:
1. A fixed `--shell-content-height: 646px` drove `.main`'s height directly — looked right on the screen it was tuned on, but a shorter viewport (a TV, or any device with less vertical space than that dev machine) made `headerBar + 646px` taller than the actual window, tipping the whole page into `body`-level scroll (a scrollbar on the far edge of the browser window, cutting off the last couple of table rows and the pagination bar).
2. Switched `.bodyBar`/`.main` to pure `flex: 1` (fill whatever's left of `100vh` after the header) — fixed the TV case, but introduced the opposite problem on a *taller* viewport (a big monitor vs. a notebook): `.main` kept growing to fill 100vh's remainder while table rows stayed a fixed height, so the same 7-row page that exactly filled the card on a notebook left a visible gap for an 8th row that never came on a monitor.
3. `.bodyBar { height: 90vh }` (a fixed *percentage* of the viewport, no `flex: 1`) was tried next, on request, on the theory that a proportional share would look identical on every device — it does not, because `vh` is *defined* to scale with the device's actual viewport height, so it produces a different absolute pixel height on every device by construction. Real screenshots across three viewport sizes proved this: one showed a visible empty gap above `Pagination`, another showed only 4 of 7 rows visible with the rest clipped off — i.e. exactly steps 1 and 2's failure modes again, just relabeled as "device classes" instead of "notebook vs. TV vs. monitor."
4. **Current shape**: back to `flex: 1` + a fixed `max-height` **in px**, on `.main` — the same fix as step 3's px-based predecessor from a different exploration branch, now confirmed to be the actual correct answer after the vh detour ruled out the alternative. `flex: 1` still lets `.main` shrink on a short viewport (the TV case from step 1 stays fixed), and the `max-height` stops it from growing past a fixed ceiling on any taller device, whether that's 20% or 200% taller (the step-2 monitor-gap case, and now also the step-3 device-class cases, all stay fixed regardless). The exact number has moved a few times on request (646 → 800, reverted for being too tall on a common ~768px-high laptop viewport, since `flex: 1` just shrinks `.main` below the cap there rather than the cap guaranteeing that height — → **700px**, the current value) — check `AdminLayout.module.css`'s `.main` for whatever it actually is now rather than trusting a number restated here. `Sidebar.module.css`'s `.aside` gets the same `max-height`, kept in sync by hand, since `.bodyInner`'s `align-items: stretch` would otherwise keep stretching the sidebar past `.main`'s cap, pushing the logout button below `.main`'s bottom edge instead of lining up with it. A viewport too short even for the cap still falls back to `Table`'s own internal scroll (invisible scrollbar, still functional via wheel/touch) — the one case that can't be avoided without literally clipping content, and strictly better than either of the two failure modes above.

Don't reach for a `vh`/`%`-based height on this container again without re-deriving why step 3 failed — the reasoning generalizes to any percentage-of-viewport approach, not just 90vh specifically. The page's root div and `Table`'s scroll wrapper are still both flex children (`.main > *` and `.scroll` respectively) so extra rows scroll *inside* `Table` — they don't grow `.main` taller — for the same reason as before: if `.main` were allowed to grow with content the Sidebar/logout button would visibly shift position with row count. `--table-row-height` keeps table rows a fixed height; `--page-title-height` keeps a page's title row the same height whether or not it includes a "Yeni X" add button. `--shell-padding-x` (60px on ≥640px viewports, 16px below) is the shell's left/right margin — `AdminLayout.module.css`'s `.headerInner`/`.bodyInner` have **no `max-width` anymore** (`--shell-max-width: 1280px` was removed by request): capping the content width made the *margin* grow with screen size instead of staying constant (a notebook, a PC monitor, and a TV each showed a visibly different left/right gutter at the same `--shell-padding-x`, since anything wider than 1280px + padding just became extra empty space on the sides) — removing the cap means the margin is always exactly `--shell-padding-x` regardless of viewport width, and the content genuinely fills the rest (this is also what exposed the wide-screen table-column gap discussed in the **`Table`** paragraph above). When adding a new list page, reuse these vars rather than hand-tuning heights, or the pages will visually drift apart again. `Pagination.module.css`'s `.wrap` padding is `4px 4px` (not the original symmetric `16px 4px`) — tightened by request, in a couple of passes, so `Campaigns`/`Categories`/`Products`/`Users`'s 7-row page size (see above) fits inside `.main` without `Table`'s `.scroll` triggering its own internal overflow (its scrollbar is already invisible per **`shared/components/Table`** above, but a few px of true overflow still made the container wheel-scrollable by a couple px, which read as the last row occasionally clipping instead of sitting fully visible above `Pagination`).

**Search flow**: the raw search string lives in `AdminLayout` (`useState`, passed to `Header`'s controlled input so typing feels instant), but the value handed down to pages via `<Outlet context={{ search } satisfies LayoutOutletContext}>` is `useDebounce(search, 500)` — so every page's `useMemo` filter (reading `search` via `useOutletContext<LayoutOutletContext>()`) only re-runs 500ms after the user stops typing. Don't debounce inside individual pages; the debounce point is centralized in `AdminLayout` so all pages get it for free. `LayoutOutletContext` (`{ search: string }`) lives in `src/types/common.ts` — it's the one type shared between the layout (producer) and every protected page (consumer), see **TypeScript**. Every page's filter compares with **`.toLocaleLowerCase('az')`, not `.toLowerCase()`** — plain `.toLowerCase()` mishandles the Azerbaijani dotted capital `İ` (JS maps it to `'i̇'`, `i` + a combining dot, not plain `i`), so searching a lowercase query against a name containing `İ` would silently fail to match under `.toLowerCase()`. Keep using the locale-aware form in any new page's filter.

**`useTitle(title)`** (`src/shared/hooks/useTitle.ts`): sets `document.title` to `"{title} · Tik Tak Admin"` for the life of the component and restores the previous title on unmount. Every page component calls it once, near the top, with its own Azerbaijani title (e.g. `useTitle('Sifarişlər')`) — do the same for any new page.

## TypeScript

The project migrated from plain JS/JSX to TypeScript in full (`tsconfig.json`, `strict: true` + `noUncheckedIndexedAccess` + `noImplicitOverride`, `allowJs: false` — there is nothing left for `allowJs` to cover). `npm run typecheck` (`tsc --noEmit`) is the only command that actually type-checks; `npm run build` transpiles via Vite/esbuild and will happily emit a broken bundle from code with type errors, so run `typecheck` (not just `build`) before calling a change done. `npm run lint` (oxlint) also covers `.ts`/`.tsx` natively — no `typescript-eslint`/ESLint in this repo — via the `typescript` plugin in `.oxlintrc.json`, which enforces `typescript/no-explicit-any: error` (see the `any`/`unknown` policy below) and warns on `typescript/consistent-type-imports` (the hard enforcement of that one is `verbatimModuleSyntax` in `tsconfig.json`, which makes a missing `import type` a compile error, not just a lint warning). There's a `src/vite-env.d.ts` for the Vite client types + the `ImportMetaEnv`/`VITE_API_BASE_URL` typing + one ambient `declare module '*.module.css'` (a single global CSS-Modules type declaration, not per-component `.d.ts` files — don't add another one).

**`src/types/` layout — every resource is a folder, `index.ts` is the only loose file at the root**: `src/types/<name>/` for `campaign`/`category`/`product`/`user`/`order`/`auth`/`api`/`common`, each with one file per type plus its own `index.ts` barrel, done on request specifically so nothing but the top-level `index.ts` sits loose in `src/types/` itself. `@/types/campaign` (same for every other name) and the top-level `types/index.ts`'s `from './campaign'` both still resolve to `<folder>/index.ts` automatically (extensionless specifier pointing at a directory), so **no other file needed an import change** on any of these moves. Import convention is unchanged by the folder split: pages may import from the top-level `types/index.ts` barrel; `lib/adapters/*.ts` and `services/*.ts` import directly from the specific resource (`@/types/campaign`, not the barrel) to keep the dependency graph flat. The four resource folders (`campaign`/`category`/`product`/`order`) follow the same four-type shape — copy this pattern for any new resource:
- `XApi` — the raw backend shape (snake_case fields like `img_url`/`created_at`, matching `docs/API.md` exactly).
- `X` — the UI/domain shape `mapXFromApi` produces (camelCase, e.g. `imageUrl`/`date`).
- `XForm` — the shape a create/edit `<Modal>` form holds in state (usually close to `X` but not identical — e.g. `ProductForm.category_id: number | string` is deliberately wider than `Product.category_id: number | ''`, because a `<select>`'s `onChange` always hands back a plain string while `openCreate`'s seed value is `number | ''`; this was a real type mismatch TypeScript caught during the migration, not a hypothetical one).
- `XPayload` — what `mapXToApi` sends on create/update (usually `Pick<XApi, ...>` of just the writable fields, no server-generated `id`/`created_at`). `User` has no `XForm`/`XPayload` (no create/edit form exists for it); `order/` has extra shapes beyond the four (`OrderItem`, `OrderItemApi`, `OrderItemProductApi`, `OrderUserShort`, `OrderStats`) since an order's nested items/user/stats don't fit the plain `XApi`/`X`/`XForm`/`XPayload` mold.
- `common/` (`BadgeColor.ts`/`Column.ts`/`IconComponent.ts`/`LayoutOutletContext.ts`) and `auth/` (`Profile.ts`/`AuthTokens.ts`/`LoginPayload.ts`/`LoginResponse.ts`/`LoginFormValues.ts`/`LoginPhoneFieldProps.ts`/`LoginPasswordFieldProps.ts`) don't follow the `XApi`/`X`/`XForm`/`XPayload` shape at all — they're small types shared across multiple resources/components (`common/`) or the login/session shape (`auth/`), not a single backend resource. `LoginFormValues` (`{ phone: string; password: string }`) is `LoginForm`'s own `react-hook-form` values type — kept in `auth/` rather than `types/shared/` since it's genuinely auth-domain like the rest of the folder, not generic UI plumbing. `LoginPhoneFieldProps`/`LoginPasswordFieldProps` are `PhoneField`/`PasswordField`'s own `Props` (each carrying a `register: UseFormRegister<LoginFormValues>`, `LoginPasswordFieldProps` additionally `showPassword`/`onToggle`) — kept alongside `LoginFormValues` in `auth/` rather than `types/shared/` for the same reason.

**The `any`/`unknown`/generics policy** (the rules actually enforced, not just a preference):
- **No bare `any` anywhere in hand-written code** — enforced by `typescript/no-explicit-any: error` in oxlint, not just a style guide entry.
- **`unknown` belongs at exactly three boundaries**: a `catch (err)` block (already `unknown` by default under `strict` — narrow with `err instanceof Error` before reading `.message`, e.g. `Login/hooks/useLoginForm.ts`'s submit handler; never re-annotate as `any`), `JSON.parse` results (`lib/auth/session.ts`'s `getStoredProfile()` does `JSON.parse(raw) as Profile` — a documented assertion, not a runtime validator, since only this module ever writes that localStorage key), and the axios response body inside `handleSuccess` before the envelope is unwrapped. Don't reach for `unknown` anywhere else as a stand-in for "didn't figure out the real type."
- **Generics exist on exactly five things**: `usePagination<T>`, `useCrudModal<TItem, TForm>`, `useDebounce<T>`, and the unwrapped `api.get<T>/post<T>/put<T>/delete<T>` calls in every `services/*.ts` file. `Table`/`Column` is deliberately **not** generic — `columns[].key` is only ever used as a React `key` + display label, never to index into row data (each page hand-writes its own `<tr>`), so a `Column<TRow>` would be speculative complexity with no bug it actually catches. Adapters are five separate concrete functions, not one generic `mapFromApi<TApi, TDomain>` — the per-resource field-renaming logic is bespoke enough that a generic mapper would type-check while doing nothing useful.
- **One sanctioned double-assertion, nowhere else**: `src/services/axiosInstance.ts` exports `api as unknown as UnwrappedApi` at the bottom of the file, because `handleSuccess` reshapes every response at runtime (unwraps the envelope) in a way axios's own `AxiosInstance` type can't express — the real `AxiosInstance` type and the post-interceptor shape are structurally incompatible by design, not by accident. `handleSuccess`'s own return type annotation (`AxiosResponse`, not what it actually returns) exists for the same reason — to satisfy axios's interceptor typing at the registration call, with a comment pointing at the real contract (`UnwrappedApi`). Don't copy this `as unknown as X` pattern elsewhere; if you hit a similar impedance mismatch, ask whether it's genuinely structural (like this one) before reaching for a cast.

**Other spots worth knowing before touching typed code**: `Button`'s `ButtonProps extends ComponentPropsWithRef<'button'>` (not `forwardRef`) — `ConfirmModal` passes `ref={cancelBtnRef}` to `Button`, and `ComponentPropsWithRef` is what lets a plain function component accept `ref` under React 19 without wrapping it. `ErrorBoundary`'s `override` keywords on `state`/`componentDidCatch`/`render` are required by `noImplicitOverride` since all three actually override members of React's `Component` base class. `noUncheckedIndexedAccess` is on — lookup tables like `ORDER_STATUS_LABELS[status]`/`PRODUCT_TYPE_LABELS[type]` are already used defensively (`?? ''`, or the key is provably non-optional going in), so this flag hasn't required new guards, just don't remove the existing ones assuming they're now redundant.
